# Ome365 v1.2 · Enterprise AI Platform Design (v3)

> **One-line repositioning**: *Governance substrate first, cockpits second.*
> v1 sold cockpits and bolted governance underneath. v2 hardened the
> governance but ran into "5 of 5 refuse / 5 of 5 won't fund."
> v3 flips the wedge: **sell the auditable file-first substrate (the
> moat); let cockpits be the daily-active product (the lock-in)**.

## 〇 · TL;DR (v3)

**Buyer** (named): **CHRO + Chief Compliance / GC at a 500–2,000 employee
regulated industry firm** (FinServ, HealthTech, RegTech, RegPharma) who
*cannot pass a 2027 EU AI Act + PIPL §38 audit on Lattice/Glean*.

**Wedge** (one sentence): *"Workday + Lattice are systems of record for
HR; they are not auditable systems of record for the AI that touched
HR. Ome365 is."*

**One ICP, one cockpit, one HRIS, one region** (v1.2 only — see §四
descope):
- ICP: 500–2,000 employee · regulated industry · EU or China primary
- Cockpit shipped: **Manager cockpit** (highest-value demo)
- HRIS shipped: **BambooHR** (cleanest SCIM 2.0); Workday/Personio CSV
  export-only in v1.2
- Region shipped: **EU primary** (GDPR Art 30 maturity); PIPL §38
  template ships but isn't load-tested until v1.3

**Honest research candor** (new §八): two open research problems we name
explicitly rather than sell as shipped: (a) provable non-leakage of an
erased subject through derived embeddings; (b) counterfactual attribution
for cost-per-business-outcome. Both are tagged "v1.4 research; v1.2 ships
a manual-re-distill workflow + sampling-audit pattern."

## 〇.4 · Eight differentiators (Round 6 · sourced from 4 analyst agents)

A competitor scan in Round 6 covered **4 product categories × 11 named
products** (Workday, Lattice, Glean, Notion AI, Mem0, Letta, Zep,
Cognee, Vanta, Drata, OneTrust + Credo/Cranium). Across those 11 there
is **no single product** that ships even 4 of the following 8.

| # | Differentiator (testable claim) | Closest comparable today |
|---|---|---|
| 1 | **HSM/KMS-backed cryptographic Right-to-Erasure**: per-subject envelope-key destruction; Art 17 / PIPL §47 verifiable by key-ID, not by DB row-delete | nobody — Lattice/Glean/Notion all rely on "deletion by policy" |
| 2 | **Per-prompt Sigstore Rekor + RFC 3161 anchoring**: every prompt/decision pinned to a public transparency log + RFC-3161-timestamped daily Merkle root; emission-completeness counter reconciled daily | nobody — Vanta journal is in-tenant; Workday journal is in-tenant |
| 3 | **Region-attested LLM routing with hard block**: provider-attested execution region (AWS STS / Anthropic header / Azure managed identity); if unattested → outbound LLM **blocked**, not warned, in PIPL §38 / GDPR Chapter V tenants | nobody — Glean does single-tenant region; nobody attests the LLM call itself |
| 4 | **WORM + crypto-shred in the same platform**: object-lock S3 / MinIO retention satisfies FINRA 17a-4(f) / SEC 17a-4 / MiFID II *and* the same record set supports GDPR Art 17 via key destruction. Mutually-exclusive regimes both pass on one substrate | nobody — Vanta has SOC2 but not WORM; QLDB has WORM but no shred |
| 5 | **3-role independent auditor signoff** for raw-prompt access (tenant-admin + DPO + auditor; for <500-ppl tenants, external attestation required) | nobody — every other vendor has 1-role admin |
| 6 | **DID-signed personal memory + manager-evidence injection**: ed25519 manager-DID signs evidence; anti-self-injection rule (manager-DID ≠ subject-DID) closes SOX 404 material-weakness gap | nobody — Lattice review comments unsigned; Mem0/Letta have no DID |
| 7 | **File-first Markdown vault + Apache 2.0 + Ollama default**: source-of-truth is portable plaintext + frontmatter; Vanta/Glean/Lattice/Notion all SaaS-tenant-locked | LangMem (SDK), Cognee (control plane) — but neither ships governance |
| 8 | **Whistleblower OWA channel bypassing tenant DLP**: Dodd-Frank §922 + EU Whistleblower Directive compliant; export goes to external notary, never appears in tenant-admin egress log | nobody — Vault is third-party for Lattice; nothing built-in elsewhere |

**Where the 11 competitors beat Ome365** (honest concessions; v1.2 will not match these):

| # | Concession | Held by | Ome365 plan |
|---|---|---|---|
| 1 | 40+ pre-built ACL-aware connectors (Slack/Drive/SF/Confluence/Jira) | Glean | not chasing; community connectors v1.4 |
| 2 | $60B HRIS depth (payroll/comp/recruiting/succession in one suite) | Workday | not chasing; integrate, don't replace |
| 3 | Calibration UX polish + 5K manager adoption pattern | Lattice | v1.3 cockpit polish pass |
| 4 | 41k stars + 80k signups + AWS Agent SDK partnership (memory layer) | Mem0 | not the same category; differentiate (see wedge below) |
| 5 | Editable memory blocks + Berkeley CS pedigree on agent runtime | Letta | not the same category; reference, don't compete |
| 6 | 400+ pre-built control mappings + auditor relationships | Vanta | partner, don't replace; map our trace to Vanta evidence |
| 7 | AI use-case intake + model registry + policy authoring workflows | Credo AI / OneTrust | partner; we are the *runtime control plane* to their *policy library* |
| 8 | Network-effect UX + collaborative editing baseline | Notion AI | not chasing; markdown export to Notion is supported |

**Category wedge** (one sentence per category):

- **vs Workday/Lattice**: *"They are systems of record for HR. We are an auditable system of record for the AI that touched HR."*
- **vs Glean/Notion**: *"They search and summarize your data. We can prove what happened to every embedding and summary derived from a subject after they exercise Art 17."*
- **vs Mem0/Letta/Zep**: *"They are SDKs that store memory and add governance later. We are governance that stores memory natively."*
- **vs Vanta/Drata/OneTrust/Credo**: *"They tell you which systems exist and which policies are written. We record what each prompt did to those systems, cryptographically."*

**Four kill questions** Ome365's pricing page can answer that no
single competitor can answer all four of:
1. Can you cryptographically prove this decision was not altered after the fact, without trusting your HRIS vendor?
2. When a subject exercises Art 17, can you produce a tombstoned audit trail for every embedding, summary, and quoted snippet derived from their data?
3. Can you replay every prompt and tool call your agent made, with an *external* auditor verifying integrity?
4. Can you produce evidence of *what your LLMs did* to your systems — not just *which systems are configured*?

**Round 6 source agents**: 4 analysts (HR-tech, knowledge-search,
AI-memory, GRC). Full transcripts archived at
`docs/strategy/v1.2-round-6-benchmark-log.md` (deferred to actual ship).

### 3.2 AI Recording · production-grade tamper-evident trace

**Trace row schema** (unchanged from v2 + 3 new fields):
```jsonl
{
  "ts": "2026-05-13T...",
  "actor_did": "did:ome365:tenant1:alice",
  "decision_id": "2026-05-13-acme",
  "prompt_hmac": "...",
  "model_id": "claude-haiku-4-5",
  "tokens_in": 1024, "tokens_out": 487,
  "cost_usd": 0.034,
  "latency_ms": 1280,
  "outcome_id": null,                  # bridged outcomes in v1.3
  "legal_basis": "art-6-1-f",
  "purpose": "decision-resolution",
  "retention_until": "2027-05-13",
  "recipient_country": "DE",           # provider-attested or "unknown"
  "transfer_mechanism": "none",
  "execution_region_attest": "aws-...", # NEW: provider signature
  "sigstore_anchor": "rekor:...",      # daily batch
  "rfc3161_token": "..."               # daily batch
}
```

**Anchoring** (revised per Kris):
- Inline: HMAC + RoPA fields. Fast path. Synchronous.
- **Daily batch**: Merkle-root the prior 24h of trace; anchor root to
  Sigstore Rekor + RFC 3161. Async with durable queue + DLQ + replay.
- **Emission-completeness attestation**: daily signed reconciliation
  of `LLM-call-counter` vs `trace-row-counter`. Posted to Rekor as a
  separate event. Auditor RBAC can verify.

**Hash policy** (unchanged from v2 + made stricter):
- HMAC-SHA256(per-tenant rotated key, redacted_prompt). Key rotated 90d.
- HMAC verifier walks key generations to validate historical rows.
- Raw prompt storage: **3-role independent auditor signoff** (tenant-admin
  + DPO + auditor — 3 distinct humans). For tenants <500 ppl where SoD
  is impossible, **external attestation required** (not "double signoff").
- PIPL §38 cross-border region: full prompt storage **structurally
  blocked** (not a toggle) until tenant deploys China Standard Contract.

**Region attestation**:
- `recipient_country` = provider-attested execution region signal.
  AWS Bedrock attests via STS, Anthropic via response header, Azure via
  managed identity. Ollama on-prem: tenant attests at deployment.
- If provider doesn't attest → field is `"unknown"` → outbound LLM is
  **blocked** in PIPL §38 / GDPR Chapter V tenants. Self-reported
  region is not acceptable for audit.

**Per-employee visibility**: per-prompt rows visible only to **auditor
RBAC**. Manager surface sees team-level aggregates (n ≥ 15) only. "Junior
burns 4× tokens" cannot be a manager query — by design.

**Operational story** (Kris):
- Trace pipeline = `LLM-router → durable queue (RabbitMQ/Kafka) →
  trace-write worker → daily Merkle batcher → Sigstore client`.
- On Rekor outage: writes continue to queue; batcher backs off; alerts
  trigger after 4h backlog. Audit gap window documented in DPIA.
- On TSA outage: switch to backup TSA (configurable list); fall back
  to Rekor-only attestation with policy flag.
- HMAC key rotation: 90d cadence; verifier loads key-generation list
  on startup; old generations retained 7y for verification.

### 3.3 Knowledge base · review queue + manual transitive erasure

**Shipping in v1.2 W6**:
- L1 Raw with per-source consent token.
- L2 Event (Hike v0.1, already shipped).
- L3 Distilled with review queue + RBAC `wiki:approve`.
- L4 Maintainer auto-merge **only** for low-risk classes (typo, link
  rot, redirect). Other edits queue for human approval.
- **Junior contribution path**: `wiki:propose` RBAC tier (below
  `wiki:approve`). Proposer credited on merge; counts toward Growth dim.

**Transitive erasure (v1.2 manual workflow)**:
- L0 erasure event → enqueue `re-distill-ticket` in admin queue.
- Affected `vault/Knowledge/` entries flagged "redaction-pending."
- Human reviewer (RBAC `wiki:approve`) decides: re-distill from
  remaining sources, OR purge entry entirely, OR mark as legal-hold
  blocked.
- sqlite-vec embeddings for affected docs are explicitly purged + rebuilt.
- Audit note: "redacted on YYYY-MM-DD per DSAR #N · reviewer:
  $auditor_did · remaining sources: N · cf. legal hold #M if blocked."

**NOT shipping in v1.2** (deferred to v1.4 research):
- **Automated re-derivation** of L3 from "remaining sources" — research
  problem. Pinecone / Weaviate / LangChain shipped nothing comparable.
- **Provable non-leakage assertion** of erased subject through cosine
  recall on rebuilt embeddings — research problem, no published technique.

**Research candor** (Kris): v1.4 publishes Ome365's embedding-leak
threat model + reference implementation. Until then, v1.2 customers
get manual workflow + a residual-risk disclosure in DPA.

## 八 · Research candor (new in v3)

Two problems we name as research, not shipping:

### 8.1 Provable non-leakage through derived embeddings

**Problem**: when subject S's L1 contributions are erased, L3/L4
distillations that already encoded S's phrasing or entity co-occurrence
patterns are *derivative works*. Rebuilding embeddings with subject
removed produces a *different* index, but does not *prove* the new
index contains zero residual signal from S's prior contributions
(near-duplicate cosine recall, n-gram bleed-through, fine-tune corpora
externalities).

**v1.2 ship**: manual workflow + tombstone + reviewer signoff +
sqlite-vec rebuild from purged source set. Customer DPA includes
residual-risk disclosure.

**v1.4 research target**: Ome365 publishes embedding-leak threat model
+ reference detection technique. Until then, "automated transitive
erasure" is not in the product narrative.

### 8.2 Counterfactual attribution for cost-per-business-outcome

**Problem**: dividing LLM cost by resolved tickets assumes the AI
*caused* the resolution. Without counterfactual (would the human have
resolved it anyway?), the metric is gameable opex inflation.

**v1.2 ship**: cost-per-resolved-decision (internal artifact, simpler
denominator) + fraud-control sampling audit + trip-wire alert.

**v1.3 design-partner work**: methodology paper. Three candidate
approaches: (a) propensity-score matched ticket cohorts pre/post AI;
(b) randomized assignment within a tenant for 90 days (consent-gated);
(c) regression-discontinuity around AI-eligibility cutoff. Publish
methodology + customer-signoff template *before* metric appears in
customer board slides.

### 8.3 Embedding-leak threat model (preview)

To be expanded in v1.4 R&D. v1.2 lists the attack surfaces we know:
- Cosine near-duplicate recall on rebuilt index
- LLM fine-tune corpora externalities (if any backend trained on prompts)
- Knowledge-graph entity co-occurrence persistence
- Backup-snapshot retention against crypto-shred timing
- Multi-tenant adjacent-data inference

## 十 · Round 7 · failure-mode stress tests (3 red-team agents)

### 10.1 Threat: insider KMS compromise (red-team analyst #1)

**Scenario**: senior insider with root on FastAPI host + AWS KMS CMK
(or Vault Transit) admin access. Patient. Goal: undetectable forgery.

**v1.2 verdict** (per analyst): **catastrophic** confidentiality +
integrity; severe non-repudiation; severe availability. v1.2 has a
single root-of-trust that collapses under a competent insider.

**Three v1.2 gaps named**:
1. **No split-trust** between L0 keystore admin and HMAC seed custody.
   Single KMS root unwraps both encryption DEKs and integrity HMAC
   keys → encryption compromise = integrity compromise.
2. **Manager-DID ed25519 keys not HSM-bound** in v1.2 spec (stored as
   OS-readable material). Shell access = signing capability.
3. **Sigstore identity unbound from tenant** in v1.2 (Fulcio ephemeral
   cert via OIDC; no enforced "only this workload identity may sign
   tenant T's batch" policy).

**v1.3 hardenings adopted** (5 of them — added to roadmap):
1. **Split-trust HMAC seed**: integrity key in Vault Transit under
   *different* admin role than KMS CMK; 2-of-3 quorum on rotation.
2. **HSM-bound manager DID**: ed25519 in YubiHSM / CloudHSM,
   non-exportable; per-call attestation signature.
3. **Merkle-mountain-range + external publication**: daily root to
   public ledger (Bitcoin OP_RETURN or CT log) — backdating breaks
   externally.
4. **Witness cosigning**: each batch co-signed by N independent
   witness nodes (cross-tenant attestation network) before Rekor
   entry accepted into our verifier.
5. **OIDC-bound Sigstore identity policy**: verifier rejects entries
   whose Fulcio subject ≠ tenant-pinned workload identity.

### 10.3 Threat: operational failures (3 sub-scenarios; SRE analyst #3)

#### 10.3.1 Vendor LLM outage

**Holds**: trace pipeline emits `router.reject` rows; daily Merkle
batcher anchors *the rejection rows themselves* to Rekor + RFC 3161.
Audit defensibility intact: "we tried, vendor was down" is
cryptographically attestable. Sigstore batch is non-empty.

**v1.3 mitigations**:
- LLM-router auto-fallback to local Ollama with `trace.degraded=true`
  + `degraded_reason=upstream_outage`; UI banner.
- Per-purpose circuit-breaker; after N consecutive rejects, flip
  purpose to `degraded` for 15min; return cached/stale coaching with
  explicit `staleness_ms`.
- Daily Sigstore manifest gains `degraded_count` + `reject_count_by_backend`;
  admin UI surfaces 24h rolling degraded ribbon.

#### 10.3.2 Departing senior dev tars vault

**Breaks**: tar contains L0 ciphertext + sqlite-vec + frontmatter
metadata (subject IDs, timestamps, DID graph — **severe metadata
leak even if plaintext stays sealed**). With KMS instance role,
dev can `kms:Decrypt` envelope DEKs on personal laptop → full
plaintext exfil. **DLP egress signing DOES NOT catch this** — it
gates the tenant-admin `/api/export/audit-pack` route, not raw `tar`
on disk. **This is a CRITICAL v1.2 gap.**

**v1.3 mitigations** (mandatory upgrade — promoted to v1.2.1 hot-patch
candidate):
- **TPM/Nitro-Enclave-bound KMS grants**: DEK unwrap only inside
  attested enclave; instance role alone yields ciphertext-only.
  Offline tar = useless blobs.
- **KMS CloudTrail → trace ingestion**: every `Decrypt` call becomes a
  `kms.decrypt` trace row with subject-DID; anomaly detector flags
  >P99 unwrap volume per principal/hour.
- **fs-level read-tripwire**: `vault/` on dm-verity + auditd `fanotify`;
  bulk-read of >1k subject blobs in <60s triggers admin alert +
  auto-revokes instance role.

#### 10.3.3 SCIM rename (BambooHR Carol Smith → Carol Jones)

**Holds with alias strategy**: DID is immutable identifier; SCIM
changes `displayName`/`userName` only. Friday's anchored trace
remains valid because leaf hash is unchanged. Crypto-shred targets
DID, not display name.

**v1.3 mitigations**:
- **Versioned canonical DID** (`did:ome365:tenant1:u_8f3a@v2`); SCIM
  writes versioned alias, never mutates ID.
- **`name_resolver` service** with 60s TTL, single source for all 6
  subsystems (vault / trace / wiki / evidence-injection / legal-hold /
  audit-pack); ban raw string-name keys in code via lint rule.
- **`scim.rename` trace row** anchored daily — rename becomes
  auditable event, not silent mutation.

2. **§10.1 KMS single-root-of-trust** → v1.2 W7 must split HMAC seed

Everything else (witness cosigning, Bitcoin OTS, FRIA template,
Shamir-split, reg-watch-list pre-shred gate, name_resolver service)
