# Ome365 v1.2 企业级AI平台设计（终版）

## 〇 · 一句话定位

**先卖可审计的、文件优先的治理底座（护城河），让cockpit成为日活产品（粘性）。**

v1把cockpit当主角，把治理当配件——结果10位评审专家5位拒签。
v4把这条主从关系倒过来。治理底座是规模化、可被监管认可的，
cockpit是底座之上才能跑起来的可视化。

---

## 〇.1 · 买家与楔子

**目标买家**（有名有姓）：**500-2000人规模的受监管行业企业的
CHRO + 合规总监/总法律顾问**。行业典型：金融科技、医疗科技、
合规科技、受监管制药。痛点一句话：**Lattice/Glean跑不通2027年
EU AI Act + PIPL §38的审计**。

**核心楔子**（一句话）：

> **Workday和Lattice是HR的record system；它们不是"动了HR的AI"的
> 可审计record system。Ome365是。**

**对四个竞品类目的分场景楔子**：

- **对Workday/Lattice**："它们是HR的系统记录；我们是动了HR的AI的可审计记录。"
- **对Glean/Notion**："它们搜索和总结你的数据；我们能证明某主体行使Art 17后，所有衍生embedding和摘要发生了什么。"
- **对Mem0/Letta/Zep**："它们是先存memory后补治理的SDK；我们是先有治理再原生存memory的底座。"
- **对Vanta/Drata/OneTrust/Credo**："它们告诉你哪些系统存在、哪些策略写好了；我们记录每条prompt对这些系统做了什么，且可密码学校验。"

## 〇.2 · 八条差异化（可验证的硬指标）

第6轮跨产品评估覆盖4个产品类目 × 11款命名产品（Workday、Lattice、
Glean、Notion AI、Mem0、Letta、Zep、Cognee、Vanta、Drata、OneTrust +
Credo/Cranium）。**这11款里，没有一款同时具备以下8条中的4条。**

| # | 差异化（可测试的命题） | 当前最接近者 |
|---|---|---|
| 1 | **HSM/KMS加持的密码学擦除权**：逐主体envelope密钥销毁；Art 17 / PIPL §47靠"key-ID销毁证据"验证，而不是"数据库行删除"凭信任 | 无——Lattice/Glean/Notion都是"按策略删除" |
| 2 | **逐prompt的Sigstore Rekor + RFC 3161双锚**：每条prompt/Decision钉到公开透明日志 + RFC-3161时间戳过的Merkle根；每日发射完整性计数器对账 | 无——Vanta的日志在租户内，Workday的journal也在租户内 |
| 3 | **区域可证明的LLM路由+硬阻断**：provider attest执行区域（AWS STS / Anthropic响应头 / Azure managed identity）；未attest则PIPL §38或GDPR Chapter V租户的出站LLM**直接阻断**，不是警告 | 无——Glean有单租户区域，但谁也不证明LLM调用本身 |
| 4 | **同平台共存WORM + 密码学擦除**：object-lock S3 / MinIO retention满足FINRA 17a-4(f) / SEC 17a-4 / MiFID II，**同一份记录**通过key销毁支持GDPR Art 17。互斥的两套监管在同一底座并行通过 | 无——Vanta有SOC2没WORM，QLDB有WORM没shred |
| 5 | **三角色独立审计签字**对raw-prompt访问（tenant-admin + DPO + auditor三位真人；<500人租户需外部attestation） | 无——其他厂商基本都是单角色admin |
| 6 | **DID签字的个人memory + 经理证据注入**：ed25519 manager-DID签字；anti-self-injection规则（manager-DID ≠ subject-DID）封住SOX 404 material weakness缺口 | 无——Lattice review评论无签字；Mem0/Letta无DID |
| 7 | **文件优先的Markdown vault + Apache 2.0 + Ollama默认**：record source是可移植的明文+frontmatter；Vanta/Glean/Lattice/Notion全是SaaS租户锁定 | LangMem（SDK）、Cognee（控制面）勉强同方向，但都没治理 |
| 8 | **绕开租户DLP的吹哨人OWA通道**：Dodd-Frank §922 + EU Whistleblower Directive合规；导出走外部公证人，不出现在租户admin的出站日志里 | 无——Lattice靠第三方Vault，其他都没内建 |

## 〇.3 · 与11款竞品的并表比较（第6轮 · 4个分析agent报告综合）

### 〇.3.1 vs Workday Performance + Workday AI (2026)

- **定位**：T1级HCM大套件，性能模块捆绑Talent/Comp/Recruiting。
  AI层：Illuminate agent家族（Recruiter/Manager Insights/Career/
  Succession）、Vibe分析、生成式review摘要、skills-cloud推理。
- **定价**：$100-300/人/月全包，Illuminate add-on约$10-15/人/月。
- **审计**：SOC 2 Type II + ISO 27001 + FedRAMP Moderate。**audit
  journal在租户内**，无公开transparency log。
- **典型客户**：Fortune 2000 / 3000人以上 / 重IT团队。
- **对Ome365目标买家的弱点**：9-18个月实施周期、首年100-300万美金、
  AI agent是黑箱（无逐决策证据链）、数据在Workday自己的租户、
  GDPR Art 17的擦除是"提删除工单"，不是key destroy。

### 〇.3.2 vs Lattice (2026)

- **定位**：中端市场"people success"平台，5000+客户，UX极强。
- **定价**：$11/人/月Talent + $4 AI add-on，捆绑约$15/人/月。
- **审计**：SOC 2 + GDPR DPA；**无FINRA 17a-4 WORM、无Rekor式
  transparency log**。
- **客户**：200-2000人科技/服务业的CHRO群体。
- **弱点**：SaaS-only（无self-host）、无HSM-backed密码学擦除、
  吹哨人模块用第三方Vault、AI prompt和输出**不可密码学attest**。

### 〇.3.3 vs Glean (2026)

- **定位**："Work AI"——企业搜索+Glean Assistants，40+ connector。
- **定价**：base约$50/人/月 + AI add-on约$15/人/月；约100人起步，
  ACV底线约6万美金，大单20-48万美金全包。
- **审计**：permission-aware RAG、SOC2、单租户部署。
- **GDPR擦除路径**：依赖**re-crawl原数据源**——下次同步时索引条目
  evict，但**对chat记录、agent memory、摘要文件的传递性派生擦除
  不发布保证**。
- **对Ome365目标买家弱点**：定价不透明、无密码学审计、agent行为
  日志描述不完整、强制起跳定价让中端受监管客户付溢价、source of
  truth留在第三方SaaS（无markdown egress）。

### 〇.3.4 vs Notion AI / Q&A (2026)

- **定位**：协同工作区+原生AI Q&A。
- **审计**：Enterprise audit log（CSV导出）、SOC2 Type II / ISO
  27001/27701；**AI specific的action approval还是个开放问题**。
- **数据驻留**：欧盟（法兰克福）、美国、2026-05新增日本/韩国——
  仅Enterprise tier。
- **弱点**：工作区就是source of truth（无中立markdown vault）、
  无逐主体密码学擦除、无防篡改审计、AI运行日志有限。

### 〇.3.5 vs Mem0 (2026)

- **背书**：Y Combinator，2025-10 Series A 2400万美金（Basis Set /
  Peak XV / GitHub Fund / YC）。
- **数据**：约41k GitHub star，1400万PyPI下载，8万云上注册；AWS
  把Mem0定为Agent SDK的独家memory provider。
- **License**：Apache 2.0 OSS + 托管云。
- **治理**：SOC 2、GDPR posture、audit log、企业tier有HIPAA/BYOK。
  擦除是delete-by-API，**无密码学销毁证明、无传递性派生擦除**。

### 〇.3.6 vs Letta（前MemGPT，2026）

- **背书**：UC Berkeley Sky/BAIR分拆，Felicis领投1000万美金。
- **数据**：主仓约6.3k star + letta-code 2.4k。
- **定位**："stateful agent"——agent runtime里memory是LLM用tool
  call编辑的一等公民block。
- **治理**：基本只有标准云控制；无audit chain、无DID。

### 〇.3.7 vs Zep / Cognee

- **Zep**：商业版，Graphiti是开源核（temporal-graph）。声称在
  LongMemEval上63.8% vs Mem0 49.0%（GPT-4o）。Credit-based定价。
  治理是标准SaaS，无DID/HMAC chain。
- **Cognee**：MIT license，约6000+ star，约70个客户logo。纯OSS
  memory控制面、embedding + graph、GitHub Secure OSS毕业生。
  **目前还没有企业治理界面**——只过了安全review。

### 〇.3.8 vs Vanta + Drata (2026)

- **数据**：Vanta约15000客户、2.2亿美金ARR、AI Agent 2.0于2026-01
  推出；Drata约8000客户、ARR1亿美金+。
- **定位**：**系统级**SOC2/ISO27001自动化合规duopoly。证据模型 =
  集成只读拉取（Vanta约375、Drata约270）配置快照然后映射到控制库。
- **对LLM审计买家的弱点**：审计的是"员工配置了哪些系统"，
  **不是"prompt看到了什么、触发了什么tool call、模型emit了什么"**。
  无Rekor锚定、无HMAC chain、无发射完整性计数器、无逐record
  密码学擦除。

### 〇.3.9 vs OneTrust + Credo AI / Cranium

- **定位**：AI治理 **策略和资产清单**层——AI use case intake、
  model registry、policy pack、RoPA/DPIA、生命周期检查点、agent
  discovery。Cranium是AI安全姿态 + 三方AI合规attestation。
- **弱点**：回答"你为这个模型写了策略吗"，**不回答"prompt号
  4812719在03:14 UTC执行时策略被严格执行了吗、能否证明它没被改"**。
  是清单+策略撰写，不是**runtime防篡改ledger**。无Sigstore Rekor、
  无RFC 3161、无prompt级别三角色审计签字。

## 〇.4 · 四问杀器（Ome365能答、单一竞品答不全四条）

1. **能否密码学证明这个决策没被事后篡改，且无需信任HRIS厂商？**
2. **当主体行使Art 17时，能否给出"每一个embedding、摘要、引用片段
   都被定位、tombstone、待重蒸馏"的可审计trail？**
3. **能否回放agent发出的每一条prompt和tool call，由外部审计人员
   独立校验完整性？**
4. **能否拿出"LLM对你的系统做了什么"的证据——而不只是"哪些系统
   被正确配置了"？**

### 2.1 四条不可破坏的不变量

1. **L2才是真理**：vault是source of truth，cockpit只是view。
2. **L0必须HSM-backed**：v1.2前提条件，没有HSM的crypto-shred就是
   纸糊的——除非客户在DPA里明确接受残余风险。
3. **L4是合规咽喉**：所有跨境路由、purpose限制、retention判断都
   在L4闸门里出，不在API层。
4. **L7是客户承诺层**：SKU、SLA、防作弊控制、TCO承诺都在L7；
   没有L7就没有可签合同的产品。

## 三 · 四大旗舰功能（v1.2诚实交付）

### 3.1 员工维度可视化 · 6维 × 5档

**v1.2 W1-W3交付**：

- **6个维度**：交付 / 质量 / 战略清晰度 / 影响力 / 成长 / 协作。
- **5档公开 + 15级内部浮点**（浮点视图带审计行）。
- **角色族adapter**：`vault/Roles/<family>.md`定义证据schema。
- **假期感知归一化**：产假、医假、sabbatical不计入业绩归一化。
- **新人模式（onboarding mode）**：入职前180天展示"在学/在建/
  在爬坡/扎实/超前"，**不展示"不达标/发展中/达标/超出/卓越"**。
  在爬坡期内任何薪酬/晋升决策不得引用band。
- **浏览器里不展示并排标量**（反立场1）。
- **AI-assist gradient规范**：每个dim × band下推荐的AI使用浓度都
  写在`docs/policies/AI_ASSIST_NORMS.md`。

**v1.2不交付（推迟到v1.3-v1.4）**：

- HR侧可编辑calibration room（v1.2只读）
- 经理宽严尺overlay（v1.2只准备数据层）
- 受保护类别公平性审计仪表板（v1.2出数据层、v1.3做UI）
- 跨组织Skill VC验证（v1.4）

**诚实坦白**（来自Jay的楔子反思）：dim系统本身**不是护城河**。
Lattice和Workday半年就能复制。**vault + audit + crypto-shred底座**
才是。v1.2先把底座做对，dim cockpit骑在底座上。

### 3.2 AI记录 · 生产级防篡改trace

**Trace行schema**（v2基础 + 3个新字段）：

```jsonl
{
  "ts": "2026-05-13T...",
  "actor_did": "did:ome365:tenant1:alice",
  "decision_id": "2026-05-13-acme",
  "prompt_hmac": "...",
  "model_id": "claude-haiku-4-5",
  "tokens_in": 1024, "tokens_out": 487,
  "cost_usd": 0.034,
  "latency_ms": 1280,
  "outcome_id": null,
  "legal_basis": "art-6-1-f",
  "purpose": "decision-resolution",
  "retention_until": "2027-05-13",
  "recipient_country": "DE",
  "transfer_mechanism": "none",
  "execution_region_attest": "aws-...",
  "sigstore_anchor": "rekor:...",
  "rfc3161_token": "..."
}
```

**锚定策略**（Kris要求修订）：

- **内联**：HMAC + RoPA字段，同步、快路径。
- **每日批锚**：把过去24h的trace Merkle化，根锚到Sigstore Rekor +
  RFC 3161 TSA。异步、durable queue + DLQ + replay。
- **发射完整性attestation**：每日`LLM调用计数 vs trace行计数`签字
  对账，作为独立事件投到Rekor。审计师有RBAC可以验。

**Hash策略**：

- HMAC-SHA256（per-tenant 90天轮转密钥，redacted prompt）。
- 验证器走多代密钥校验历史行。
- **raw prompt存储**：**三角色独立审计签字**（tenant-admin + DPO +
  auditor三位不同的真人，写进`rbac-matrix.md`）。SoD不可能的<500人
  租户**必须用外部attestation**——不是"双签字"那么轻。
- **PIPL §38跨境**：full prompt存储**在结构上被阻断**（不是开关），
  直到租户部署China Standard Contract。

**区域attest**：

- `recipient_country` = provider attest的执行区域信号。AWS Bedrock
  靠STS、Anthropic靠响应头、Azure靠managed identity。Ollama本地：
  租户在部署时attest。
- provider不attest → 字段为`"unknown"` → PIPL §38 / GDPR Chapter V
  租户的出站LLM被**阻断**。自报区域不算合规依据。

**逐员工可见性**：单prompt行只对**audit RBAC**可见。经理界面看
团队级聚合（n ≥ 15）。"应届员工烧了4倍token"**不可作为经理查询**——
这是设计意图。

**运营故事**（Kris）：

- trace管线 = `LLM router → durable queue (RabbitMQ/Kafka) →
  trace-write worker → 每日Merkle batcher → Sigstore client`。
- Rekor outage：写继续进queue；batcher退避；4h backlog报警。审计
  gap window写进DPIA。
- TSA outage：切到备用TSA（可配置列表）；fallback成Rekor-only。
- HMAC key轮转：90天周期；启动时加载多代列表；老代保留7年用于
  历史验证。

### 8.1 通过派生embedding的不可泄漏证明

**问题**：当主体S的L1贡献被擦除，已经把S的措辞或实体共现pattern编码
进L3/L4的产物是**衍生作品**。用"去掉S"的数据集重建embedding会
产生**不同的**索引，但**不能证明**新索引对S的先前贡献零残留信号
（近重复cosine recall、n-gram透射、fine-tune corpus外部性）。

**v1.2交付**：人工workflow + tombstone + reviewer签字 + 从purged
数据源rebuild sqlite-vec。DPA披露残余风险。

**v1.4研究目标**：Ome365发表embedding leak threat model + reference
detection。在此之前，"自动传递性擦除"不进产品叙事。

### 8.2 cost-per-business-outcome的counterfactual归因

**问题**：把LLM成本除以resolved ticket数假设AI**导致**了resolve。
没有counterfactual（同一个人**没有**AI会不会也resolve？），指标就
**可以被opex膨胀地玩**。

**v1.2交付**：cost-per-resolved-decision（内部artifact、更简单的分母）
+ 防作弊采样审计 + 挂钩率挂钩警报。

**v1.3 design-partner工作**：方法论paper。三个候选approach：
(a) 倾向性score-matched ticket cohort pre/post AI；
(b) 租户内随机分配90天（consent-gated）；
(c) AI-eligibility cutoff附近的regression discontinuity。
**先发表方法论 + 客户签字模板，再让指标进客户board slide**。

- rebuilt索引上的cosine近重复recall

## 十 · 第7轮压力测试三战场总结（红队3 agent）

### 10.1 内部insider KMS妥协（红队 #1）

**场景**：senior insider有FastAPI shell + AWS KMS CMK admin（或Vault
Transit）。耐心。目标是**不可检测的forgery**。

**v1.2评级**：**catastrophic** 机密性 + 完整性；**severe** 不可否认；
**severe** 可用性。**v1.2有single root of trust，competent insider
能在不留痕迹的前提下拆掉它。**

**3条v1.2缺口**：

1. L0 keystore admin和HMAC种子保管**未隔离**。单KMS root同时解
   加密DEK和完整性HMAC key → 加密妥协 = 完整性妥协。
2. manager-DID ed25519**未HSM绑定**（v1.2 spec默认存为OS可读）。
   shell访问 = 签字能力。
3. Sigstore身份**未绑定tenant**（Fulcio ephemeral cert靠OIDC；
   无强制"只允许这个workload身份签T租户的批"策略）。

**v1.3硬化方案**（5条已进roadmap）：

1. **split-trust HMAC种子**：完整性key进Vault Transit的**不同**
   admin角色；2-of-3 quorum轮转。
2. **HSM绑定的manager DID**：ed25519进YubiHSM / CloudHSM不可导出；
   每次调用都需要attestation签字。
3. **Merkle Mountain Range + 外部发布**：每日root发到公链（Bitcoin
   OP_RETURN或CT log）——backdating外部就破。
4. **Witness cosigning**：每批由N个独立witness节点联签（跨租户
   attest网络）后才接受进Rekor。
5. **OIDC绑定的Sigstore身份策略**：verifier拒绝Fulcio subject与
   tenant-pinned workload身份不符的entry。

### 10.3 运营失效（SRE红队 #3 · 3个子场景）

#### 10.3.1 vendor LLM outage

- **Anthropic API 4h区域outage，50个经理cockpit用户9am集体撞墙。**
- **保住的**：trace pipeline健康；router fast-fail emit
  `router.reject{purpose, backend, reason=upstream_429, ttl_ms}`行；
  queue drain；每日Merkle batcher**把reject行本身锚到Rekor + RFC 3161**。
  审计defensibility完整：**"我们试了，vendor挂了"是密码学可证的**。
  Sigstore批非空——reject row也是row。
- **v1.3缓解**：
  - LLM router自动fallback到本地Ollama，trace带`degraded=true` +
    `degraded_reason=upstream_outage`；UI banner"运行在本地模型上，
    质量降级"。
  - 每个purpose的circuit breaker：N次连续reject后flip purpose到
    `degraded`持续15分钟，返回cached/stale coaching分析并显式标注
    `staleness_ms`。
  - 每日Sigstore manifest新增`degraded_count` + `reject_count_by_backend`；
    admin UI显示24h滚动degraded ribbon。

#### 10.3.2 离职senior dev打包vault

- **场景**：senior dev在FastAPI host上有sudo，他离职前tar
  `/var/ome365/vault`传到个人Dropbox。
- **破的**：tar里有L0密文blob + sqlite-vec + markdown frontmatter
  （subject ID、时间戳、DID图）——**metadata泄漏严重**，即使明文未泄。
  有KMS instance role的情况下dev能在个人laptop上`kms:Decrypt`
  envelope DEK → 完整明文exfil。
- **DLP egress签字不catch这个**——它gate的是tenant-admin
  `/api/export/audit-pack`路由，**不是磁盘上的raw `tar`**。WORM S3
  不受影响（object lock防删不防读）。Sigstore锚证明事后没篡改，
  但说不出**谁读过**。
- **这是v1.2严重缺口**。**v1.3缓解**（建议升级为v1.2.1热修）：
  - **TPM/Nitro Enclave绑定的KMS grant**：DEK unwrap只能在attested
    enclave里发生；单独的instance role只能拿到密文blob。**离线
    tar = 废blob**。
  - **KMS CloudTrail → trace管线消费**：每条`Decrypt`变成`kms.decrypt`
    trace row带subject DID；异常detector flag每principal每小时
    >P99 unwrap量。
  - **fs级read tripwire**：`vault/`挂dm-verity + auditd `fanotify`；
    >1000个subject blob在<60秒内被bulk读触发admin alert + 自动
    撤销instance role。

#### 10.3.3 SCIM rename（BambooHR Carol Smith → Carol Jones）

- **场景**：Carol结婚改姓。SCIM 3am同步。Carol的vault entry keyed
  on `did:ome365:tenant1:carol-smith`。她周五的trace row用老DID。
  L4 wiki backlink用老名。Crypto-shred事件以"carol-smith"为key
  会不会影响"carol-jones"？
- **alias策略下保住的**：DID是immutable identifier；SCIM只改
  `displayName`/`userName`。周五锚定的trace仍有效——leaf hash未变。
  Crypto-shred targets DID而非display name。
- **6个子系统走查**：
  - vault：frontmatter `subject_did`不变；`display_name`更新；老名
    进`aliases[]`。
  - trace：零rewrite；resolver在render时把DID映射到当前name。
  - wiki：backlink靠DID resolve；老名字串搜过alias index命中。
  - 证据注入：cache key on DID，不受影响。
  - legal hold：scope on DID，rename不影响hold。
  - audit-pack：manifest emit `alias_history` block。
- **v1.3缓解**：
  - **canonical DID带版本** (`did:ome365:tenant1:u_8f3a@v2`)；SCIM写
    versioned alias，**永不**mutate ID。
  - **`name_resolver`服务**带60秒TTL，6个子系统的单一source；用
    lint规则禁止代码里用raw字符串name做key。
  - **`scim.rename`** trace行每日锚——rename变成可审计事件，不是
    无声mutation。

### 10.4 第7轮verdict + back-port决定

1. **§10.3.2 vault tar exfil** → v1.2 W7必含TPM/Nitro enclave绑定

## 三.6 · Scoring Policy spec（catastrophic缺口 · 能力工程师评审 #2）

> r5.0说"6维 × 5档 × 15级浮点"但未明示**谁打分 · 怎么算 · 怎么reconcile**。
> 这是产品能不能跑的命门。

### 三层打分模型 · v1.2交付

| 层 | source | 输出粒度 | 写入路径 | 签字 |
|---|---|---|---|---|
| **L1 manager 打分** | Bob每季度session | 5档（不直接打浮点） | `vault/Reviews/<emp>/<quarter>.md` frontmatter | manager-DID |
| **L2 AI聚合sub-score** | trace + Decision + PR + ticket聚合 | 6维各一个15级浮点 | 同上frontmatter里`ai_subscores`字段 | AI-DID（系统签字） |
| **L3 reconciled展示** | L1 × 0.7 + L2 × 0.3（W2确认） | 公开5档 + 内部15级浮点 | derived view，不持久化 | 二者签字+reviewer审批 |

### Override规则

- manager对AI sub-score不认 → 在review里加`ai_override: true`+`override_rationale`字段
- override事件进trace（带manager-DID + AI-DID + Δ值）
- 季度末**override率>20%的manager**进calibration时被Carol拉单聊
- override不可逆——下季度AI重训需要展示override分布

### Anti-gaming控制

- manager连续3次override同一员工 → 自动触发HR fairness audit
- AI sub-score算法**透明** + 客户可查看权重在`docs/policies/SCORING.md`
- 浮点不是黑箱回归——是规则聚合（trace count权重 + Decision close rate权重 + PR merged权重 + peer feedback权重）
- 详细算法 spec见附录F
